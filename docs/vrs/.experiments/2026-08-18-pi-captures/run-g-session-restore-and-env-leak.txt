# Session-start restore, tool-call round trip, and env-leak check

## What ran
A pi seat under 'st2 up' with durable working state and one unread message written BEFORE boot.
The fake provider answers the boot prompt with a real bash tool call that prints whether st2's
channel variables and pi's own session variables are visible to a tool child.

## Provider requests (roles, and whether restored context is present)
{"roles":["system","user","user"],"hasRestoredContext":true}
{"roles":["system","user","user","assistant","tool","user"],"hasRestoredContext":true}

The FIRST model call already carries the restored context: the extension awaits the channel's
hello inside session_start, so restoration is ordered before the boot turn rather than after it.

## Tool-call round trip, and the environment check it ran
LEAK_CHANNEL=0
PI_SESSION_ID_SET=yes

LEAK_CHANNEL=0  -> a bash tool child sees no ST2_PI_CHANNEL_* at all. The extension takes them
                   out of the environment on first load, so a nested pi cannot inherit its
                   parent's bus identity or inbox.
PI_SESSION_ID_SET=yes -> pi's OWN session variables DO reach tool children, which is why the
                   eval seat scrub adds PI_* beside the existing CLAUDE_*/CODEX_* entries.
