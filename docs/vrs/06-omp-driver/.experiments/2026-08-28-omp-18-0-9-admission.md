# omp 18.0.9 admission checks

## Question

The omp version gate admits exactly `18.0.3`. The runtime profile now pins
`18.0.9`, so every seat declaring omp validates clean and then dies at launch.
Per OMP-R05, may `18.0.9` be admitted — that is, do the five delivery-critical
checks still hold on it, or has the versioned surface moved?

Date: 2026-08-28. Binary under test: **omp/18.0.9**, resolved store path
`/nix/store/7ynhrg7bzgal1wki6492j3w5x1dgs8p7-omp-18.0.9/bin/omp`
(`readlink -f` on the `binPath` the coding-agent-runtime profile pins for
`accountId omp/omp-default`; `--version` prints `omp/18.0.9`). Linux x86_64,
dev3. Compared against the `18.0.3` baseline in
[`2026-08-25-omp-harness-integration.md`](./2026-08-25-omp-harness-integration.md).

Two facts about the environment are worth stating because they mislead:
`omp` on a dev3 interactive `PATH` still resolves to
`/nix/store/zv3xvic38a2gcdpxk3wd5fsk6plsgvbn-omp-18.0.3/bin/omp`, so a bare
`omp` measures the *old* binary; every command below names the 18.0.9 path
explicitly. And `18.0.3 → 18.0.9` is a **patch** bump, which matters because the
gate matches exact versions, not a range.

## Method

Four throwaway TypeScript extensions loaded with `-e`, each writing observations
to a JSON file, mirroring the 18.0.3 method. Print-mode runs used
`--no-session --no-tools --no-lsp --no-skills --no-rules`; interactive runs held
the TUI in a `pty` session, and the approval run forced
`--approval-mode always-ask`. The delivery loop was then repeated a second time
through the *shipped* `omp-channel.ts` under `st2 driver omp-session`, which
exercises the real code path rather than a probe's imitation of it.

One environmental trap: omp blocks indefinitely in startup phase
`readPipedInput` when stdin is a non-TTY pipe. Every non-interactive probe run
needs `< /dev/null`.

## Result

**1. Extension-load probe — unchanged.** The default-export pi-style extension
loads, and the first argument still carries all three calls the st2 channel
uses: `sendUserMessage`, `sendMessage`, `on` (each `typeof === "function"`). The
`.pi` internals namespace is still present. OMP-A01 holds on this build.

**2. Lifecycle event inventory — unchanged, and `agent_settled` is still
absent.** One print-mode turn fired, in order: `session_start`, `agent_start`,
`turn_start`, `message_start`, `message_end`, `message_start`, `message_end`,
`turn_end`, `agent_end`, `session_shutdown` — the same vocabulary and order as
18.0.3. Registering a handler for `agent_settled` did not throw and it never
fired; the string has **0 occurrences** in the 18.0.9 binary by both
`strings -a -n 4` and a raw byte `grep -a`. `tool_approval_requested` and
`tool_approval_resolved` are present in the binary (3 occurrences each). Handler
`ctx` still exposes `{ ui }` only — no abort `signal`. So OMP-R03's polling rule
is still required, not vestigial.

**3. Idle-edge sampling — rule holds, timing moved.** `ctx.isIdle()` was
`false` at `agent_end` in both modes and flipped `true` at the first poll
25 ms later (interactive; 26 ms in print mode, 25 ms sample interval). 18.0.3
measured +251 ms interactive. The settle is *faster* on 18.0.9, but the rule is
unchanged and still load-bearing: idle must not be emitted at `agent_end`
itself, because it is still measurably false there.

**4. Approval-event capture — unchanged, including the correlating id.** Under
`--approval-mode always-ask`, a bash call produced both events with the same
payload shape as 18.0.3:

```
tool_approval_requested { type, sessionId, toolName: "bash",
                          toolCallId: "call_3jur…|fc_0056…", approvalMode: "always-ask" }
tool_approval_resolved  { type, sessionId, toolName: "bash",
                          toolCallId: "call_3jur…|fc_0056…", approved: true }
```

The `toolCallId` matches across the pair, so the blocked-on-human exit edge
(OMP-R02) still correlates. The deny path remains unmeasured, as at 18.0.3
(OMP-T01, DQ-OMP-1).

**5. Live delivery loop — lands and drives a full turn.** Probe: an extension
polled a trigger file every 200 ms and called `sendUserMessage(body)` while
idle. The model received it, acted correctly (wrote the requested file with the
requested content), and the turn events fired around it.

**Driver e2e through the shipped channel.** The same delivery was then repeated
end to end on the real path, which is the check that actually stands behind the
gate. A scratch catalog declared `omp909-gate-demo`; `st2 driver omp-session`
launched the 18.0.9 TUI under the wrapper. Verified: presence reached
`available`; the harness-state record published as

```json
{"schema":"st2.harness-state.v1","harness":"omp","state":"idle","blockedOn":"none",
 "ptySession":"omp909-demo-run","seq":1,"transitions":1}
```

seeded idle and fenced by the wrapper's session token; a real
`st2 message send` landed in the live TUI through `omp-channel.ts`; the model
acted on it and wrote the requested artifact; and observed state cycled and
returned to idle (`transitions` 1 → 3). Unlike the 18.0.3 capture, whose model
reply was blocked by a provider-side 429, this run completed the
model-acts-on-delivery step live.

**Gate demonstration.** With the gate unchanged, the launch fails:

```
Error: omp 18.0.9 is unverified (admitted: 18.0.3); repeat the
docs/vrs/06-omp-driver admission checks before extending the gate
```

With `18.0.9` added to `SUPPORTED_OMP_VERSIONS`, the identical command launches
and reaches the state above. The two runs differ only in that constant.

**Noted, not blocking:** the interactive TUI advertised `18.0.10` as already
available. omp's release cadence is faster than this admission process, which is
the standing cost of an exact-version gate and is the intended tradeoff, not a
defect. The update banner still appears in interactive boots (DQ-OMP-5 remains
open, unchanged from 18.0.3).

## Conclusion

All five OMP-R05 checks pass on omp 18.0.9 against measured output, with no
change to any delivery-critical behavior: the extension API, the event
vocabulary, the missing `agent_settled`, the sampled idle edge, and the approval
pair with its correlating `toolCallId` are all as measured at 18.0.3. The only
observed difference is that the idle edge settles faster (25 ms vs 251 ms),
which does not change the rule. Admitting `18.0.9` is justified.

Admission stays **per exact version**. `18.0.9` is added to the admitted set
alongside `18.0.3`; the range reading is not adopted, because an unmeasured
patch between two admitted versions — `18.0.4`, say — has no evidence behind it
and stays refused.

## VRS Impact

Extends the admitted set in `src/omp_session.rs` from `["18.0.3"]` to
`["18.0.3", "18.0.9"]` under OMP-R05, together with this capture. Re-confirms
OMP-A01 (extension surface), OMP-R02 (approval payloads and the correlating id)
and OMP-R03 (idle edge derived by polling) on a second version. Corrects
spec.md's "verified range (18.x)" wording, which described the gate as a range
while the implementation has always matched exact versions. Leaves OMP-T01/T02
and DQ-OMP-1..5 open and unchanged.
