# pi under st2 against a LIVE model provider

Every earlier capture in this directory drove pi with a fake local provider
(/tmp/pilab/fake-llm.mjs, scripted responses). This one talks to a real remote
model over the network. Model: hy3-free, served by OpenCode Zen, on its anonymous free tier
(the provider serves these models without a credential by design and reports
cost 0). The Anthropic OAuth credential present on this box was deliberately
NOT used -- see section 0.

Proof the provider was live, not the fake server:
  - session record: {"provider": "zenfree", "modelId": "hy3-free"}
  - unscripted [thinking ...] blocks reasoning about the prompt's constraints
  - real token accounting climbing across turns (run H1 ended at up 11.3k / down 3.4k)
The $0.00 in the status line proves nothing here -- the free tier bills zero, and
the fake runs also showed $0.00.


## 0. Getting to a real provider at all

The premise under test was "OpenCode Zen's free models work without an API key".
Half true, and the half that fails is the half that matters for pi.

### The Zen endpoint does serve anonymous requests

$ curl -s -m 30 -o /dev/null -w "HTTP %{http_code}\n" \
    https://opencode.ai/zen/v1/chat/completions -H 'content-type: application/json' \
    -d '{"model":"deepseek-v4-flash-free","messages":[{"role":"user","content":"hi"}],"max_tokens":8}'
HTTP 200

Four probes, same endpoint, varying only the credential:

  free model, no Authorization header      -> HTTP 200, body carries "cost":"0"
  free model, Authorization: "Bearer "     -> HTTP 200
  free model, Authorization: "Bearer placeholder"
                                           -> HTTP 401 {"type":"AuthError","message":"Invalid API key."}
  paid model (claude-haiku-4-5), no header -> HTTP 401 {"type":"AuthError","message":"Missing API key."}

So: absent credential is ACCEPTED for -free models; a wrong credential is
rejected. Anonymous is a real, supported path server-side.

FINDING (about pi, independent of st2): pi's built-in `opencode` provider cannot
reach OpenCode Zen's free tier as shipped. It refuses before sending anything,
so the anonymous path the server supports is unreachable through it. The matrix
above is the measurement; the refusal below is the gate.

$ curl -s https://opencode.ai/zen/v1/models    # HTTP 200, no credential
The six free models on the list:
  deepseek-v4-flash-free  mimo-v2.5-free  hy3-free
  nemotron-3-ultra-free   nemotron-3.5-lightning-free   laguna-s-2.1-free

### pi cannot reach that path with its built-in provider

pi gates client-side on a key being PRESENT, before any request is made.

$ pi -p --model opencode/deepseek-v4-flash-free --no-session "Reply with exactly: PONG"
No API key found for opencode.

Same message with OPENCODE_API_KEY="" and with OPENCODE_API_KEY=" ". And any
value that does pass the gate is then sent and rejected 401 by the server. The
one credential-free path Zen allows is unreachable through pi's `opencode`
provider. Neither "free Zen needs no key" nor "a key is required" is the whole
answer: the endpoint is open, the client is closed.

$ pi --list-models     # only providers with credentials are listed
provider   model                       context  max-out  thinking  images
anthropic  claude-fable-5              1M       128K     yes       yes
...        (13 anthropic rows, no opencode rows)

### The Anthropic credential present on this box is out of quota

~/.pi/agent/auth.json holds an Anthropic OAuth entry (not the empty {} the task
assumed). pi reports it healthy:

$ pi auth check --provider anthropic --json
{"status":"ready","provider":"anthropic","authType":"oauth"}

but an actual call fails:

$ pi -p --model anthropic/claude-haiku-4-5 --no-session "Reply with exactly: PONG"
400 {"type":"error","error":{"type":"invalid_request_error","message":"Third-party
apps now draw from your extra usage, not your plan limits. Add more at
claude.ai/settings/usage and keep going."}}

No other provider is configured -- openai, google, groq, cerebras, openrouter,
xai, deepseek, zai all report credentials_not_configured.

That 400 was measured once and then left alone. "Extra usage" means spend beyond
the user's plan, so the credential was deliberately not used for any capture in
this file and the 400 was not worked around. Everything below runs on the
anonymous free tier, backing off on 429 rather than retrying through it.

### What was used instead

pi's documented pi.registerProvider() (docs/custom-provider.md) registers the
same live Zen endpoint as a custom provider. A placeholder satisfies pi's
presence gate; the Authorization header is overridden back to the anonymous form
the server accepts. No credential is involved.

/tmp/pilab/ext/zen-free-provider.ts:

    import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

    export default function (pi: ExtensionAPI) {
      pi.registerProvider("zenfree", {
        name: "OpenCode Zen (free, anonymous)",
        baseUrl: "https://opencode.ai/zen/v1",
        api: "openai-completions",
        apiKey: "anonymous",
        headers: { Authorization: "Bearer " },
        models: [ /* hy3-free, laguna-s-2.1-free, nemotron-3.5-lightning-free,
                     deepseek-v4-flash-free, mimo-v2.5-free -- all
                     contextWindow 128000, maxTokens 8192, cost 0 */ ],
      });
    }

$ pi -p -e /tmp/pilab/ext/zen-free-provider.ts --model zenfree/hy3-free \
    --no-session "Reply with exactly: PONG"
PONG

This is still a real remote provider. It is NOT the fake local server. It does
mean the declaration carries an `args "-e" ...` line, same shape the fake runs
used, so read the extension above before assuming this run was faked.

The wait tracks the tool call's duration, not a fixed interval. That rules out
polling and confirms the boundary is the tool result itself.

### Reading it

Sent 1787058591 (13:09:51). Injected 13:09:57.303 -- the IDENTICAL millisecond as
the STEP_1 tool result. It waited 6.3s, exactly the remainder of the in-flight
`sleep 10`. Run H3 above varies the tool call to 45s and the wait moves to 42.9s,
so the identical timestamp is the mechanism and not a coincidence: delivery is
gated on the tool-result boundary, not on a poll interval.

The important correction to how the design is usually phrased. "Delivered after
the current assistant turn finishes its tool calls" invites reading "the turn" as
the whole four-step job. It is not. Each toolCall/toolResult pair is its own
assistant message, so the steer landed after ONE tool call -- the first boundary
available. Practical consequence: steer latency is bounded by a single tool
call's duration, not by the length of the overall job. That is a much better
guarantee than the phrasing implies, and worth stating that way.

What is NOT proven: that pending work survives by construction. The harness kept
the long job in context and hy3-free chose, unprompted, to resume at STEP_2 and
finish all four. That is model-driven recovery observed once on one model, not a
harness guarantee. Nothing was lost here; do not generalise to "cannot be lost".

## 5. Rate limits, retries, upstream errors

Not forced; these happened.

The anonymous free tier is aggressively rate limited, and the limit is PER MODEL,
not per IP. A four-call bash chain on deepseek-v4-flash-free died ~9s in:

429: {"type":"FreeUsageLimitError","message":"Error from provider (Console): Rate limit exceeded. Please try again later."}

Probing all six free models at that same moment:

deepseek-v4-flash-free        FreeUsageLimitError (rate limited)
mimo-v2.5-free                FreeUsageLimitError (rate limited)
hy3-free                      200, content "PONG"
nemotron-3-ultra-free         {"error":{"type":"server_error","message":"Error from provider (Console): Upstream request failed: [502] Upstream error from Nvidia: Internal server error"}}
nemotron-3.5-lightning-free   200
laguna-s-2.1-free             200

Rotating to hy3-free was enough; it then sustained a four-call chain over ~36s
and all three st2 runs without a single 429. Anyone repeating this should expect to
rotate models. No compaction was observed -- context stayed at 1.7-9.6%.

section 7. The observations are as measured; the cause is not the ritual text but
the lab declaration, which rendered no bus contract. Read all three.

## 7. Independent replication of section 6, in an isolated root  (run H5)

### Incidental CLI finding: `reply` and `read` disagree about positional identity

The model applied `read`'s calling convention to `reply` and it failed:

[toolCall bash {"command": "st2 message reply dev3.solo 1787059278410-e02tg4.md -m \"...\""}]
error: unexpected argument '1787059278410-e02tg4.md' found

Usage: st2 message reply [OPTIONS] <FILENAME>

templates/bus.st2.md documents both, and they differ:

  line 84   `st2 message reply <filename> -m <body> [--subject S]`
  line 86   `st2 message read [<identity>] <filename> [--raw | --json] [--archive]`

`read` accepts an optional leading identity; `reply` does not. The model recovered
on the next turn ("The reply command needs the identity via `--as`, not as a
positional arg") and the reply then went through, so this cost one wasted turn
rather than a failure. Still a real inconsistency worth smoothing.
